# Why Email HTML Often Breaks Across Clients

Email clients use a **wide variety of rendering engines and policies**, so HTML that looks fine in one inbox may “break” in another. Major factors include:

- **Different rendering engines:**  For example, **Outlook (Windows)** uses the Microsoft Word engine to display emails, which has *extremely limited CSS support*. It ignores many modern CSS features (floats, padding, margins, background images, etc.), causing layouts to collapse【10†L82-L90】【13†L339-L347】. In contrast, **Apple Mail (macOS/iOS)** uses WebKit (Safari’s engine) and is highly standards‑compliant – if it works in a browser, it usually works there【17†L273-L281】. **Gmail (web)** uses a Chromium-based renderer that supports most CSS (when used in the `<head>` or inline)【3†L311-L319】, and **Outlook.com**/New Outlook (Windows Post-2025) now also uses a Chromium engine with modern CSS support【17†L248-L257】. These engine differences mean an email might display one way in Outlook Windows versus Gmail versus Apple Mail, etc.

- **CSS support limitations:** Most email clients support only a **subset of CSS**. As Litmus notes, “not all CSS properties are supported in email clients…stick to widely supported styles and avoid complex CSS”【26†L1-L4】. For example, Outlook desktop **ignores CSS floats, padding on tables, and background images**【10†L82-L90】【13†L339-L347】. Gmail strips any CSS placed outside the `<body>` and historically had quirks (e.g. it would drop entire inline styles if punctuation wasn’t spaced)【21†L174-L182】【21†L242-L250】. Yahoo Mail has odd bugs (e.g. it converts `height` to `min-height`, breaking responsive images, and it removes CSS below HTML comments)【17†L319-L327】【17†L338-L347】. In short, a CSS rule you rely on in a browser may be ignored or garbled by some email client.

- **Sanitization and style stripping:** Many clients and services *sanitize HTML for security*. For instance, some webmail (especially older versions of Gmail) **remove `<style>` blocks or external CSS links**, leaving only inline styles【21†L174-L182】. Scripts, iframes, forms, and other interactive tags are usually stripped or disabled entirely【27†L297-L304】. If your template uses `<script>`, `<video>`, `<iframe>`, or even CSS `@import`, the client will simply omit them, breaking your design. (Only a few clients support embedded video, e.g. Apple Mail; most will not【32†L182-L190】.) Similarly, JavaScript is *universally* blocked【27†L297-L304】, so any dynamic code will be removed.

- **Layout and HTML structure issues:** Many emails rely on `<table>` layouts to keep columns aligned. If you use `<div>`-based or CSS-grid layouts, **some clients (especially Outlook)** may collapse or ignore them【27†L299-L307】. Failing to include a proper `<!DOCTYPE html>` can trigger “quirks mode” in some clients, making things look messy【34†L121-L129】. For example, Email on Acid warns that without the right DOCTYPE, an email “will probably not display as you intended over multiple email clients”【34†L121-L129】. Missing `<meta charset="UTF-8">` can also garble non-ASCII text. 

- **Image and media blocking:** Many clients **block external images by default** (requiring the user to click “display images”). If your layout uses background images, logos, or spacer GIFs, the missing graphics can break alignment or make text unreadable. EmailonAcid advises avoiding background images because “Outlook desktop…will automatically disable images… If you use light text on a dark background image, [users] may see blank white background”【37†L211-L219】. Likewise, image-based buttons (CTAs) will vanish if images are off. Always include descriptive `alt` text on images (so the message still makes sense when images are blocked)【39†L94-L101】.

- **Client-specific quirks:** Beyond general rules, each client has its own oddities. For example:  
  - **Outlook (classic):** Needs MSO-conditional comments and VML hacks. Many developers wrap modern HTML in “ghost tables” visible only to Outlook, or use VML (`<v:rect>`) for background images【17†L204-L212】【17†L227-L236】.  
  - **Gmail:** Now supports `<style>` in the head, but older Gmail ignored it and demanded inline CSS【21†L174-L182】【3†L311-L319】. Gmail (mobile) also auto‑inverts dark colors (no custom control)【17†L379-L383】.  
  - **Yahoo Mail:** Has several unique bugs: it *converts any `height:auto` to `min-height:auto`* (breaking scaling)【17†L319-L327】, strips `!important` if you put a space before it【17†L324-L332】, and removes CSS rules under HTML comments【17†L338-L347】. Yahoo also doesn’t invert colors in dark mode (it leaves emails as-is)【17†L343-L347】.  
  - **Samsung Email (Android):** Its biggest quirk is the width: it uses the HTML `width` attribute (not CSS) to determine viewport. If you have `<table width="600">`, Samsung will render at 600px-wide no matter what, potentially breaking fluid layouts【17†L351-L360】. Also, margin padding support is inconsistent (e.g. `margin` works on `<p>` tags but not on `<div>` or `<table>`【17†L363-L368】).  
  - **Dark mode differences:** Clients handle dark mode unpredictably. Apple Mail, Outlook for Mac, and Thunderbird allow media-query dark CSS【17†L377-L383】, but Gmail and many mobile clients will auto-invert colors and **ignore** your dark styles【17†L379-L383】. If your email has dark background/light text, it may be inverted to light-background/dark-text (or vice versa) on some apps.

- **Responsive/mobile issues:** Without careful responsive design, emails can break on phones. Some clients (like older Outlook) simply ignore media queries, so you must design “mobile-first” using fluid tables. Samsung’s viewport bug above is one example. Also, limit the overall width to ~600px: testing shows Yahoo and Outlook break layouts above ~650px【32†L177-L185】, so sticking to 600px or less prevents horizontal cut-off【39†L53-L58】. 

In summary, **the same HTML/CSS can behave very differently in each inbox**. Email clients inconsistently support modern web standards, strip or alter CSS/HTML for security, and have unique bugs. The result is that complex layouts, unsupported CSS, or blocked content will be “disturbed” (messed up) unless you code defensively and test broadly.

# Email HTML Checklist: What to Include vs. What to Avoid

To maximize compatibility **include** these practices in your email code, and **avoid** the listed pitfalls:

- **Include:**  
  - A proper `<!DOCTYPE html>` (ideally HTML5) and `<html lang="…">` declaration at the top. This ensures “standards mode” rendering; without it clients may fall into quirks mode and break layouts【34†L121-L129】【34†L176-L180】.  
  - A `<meta charset="UTF-8">` tag so characters display correctly.  
  - Table-based structure for main layout (nested `<table>`s), since tables render consistently across clients【27†L299-L307】. Use the old HTML alignment attributes (e.g. `align="center"`) or table cell structure for centering (rather than CSS centering).  
  - Fixed widths on tables/cells for desktop design. When necessary, use inline CSS **width** (or the `width` attribute for older clients) on tables and images. Remember Samsung: using `width="100%"` on images and container tables helps force responsiveness【17†L351-L360】.  
  - Inline CSS styles on every element (especially for colors, fonts, sizes). As Gmail’s support docs stress, you can put CSS in `<style>` in the head【3†L311-L319】, but **inline** styles are safest across all clients【21†L174-L182】.  
  - Web-safe font stacks and fallback fonts. Since custom/web fonts have spotty support, always list at least a common font (Arial, Helvetica, sans-serif) as a fallback【27†L412-L417】.  
  - Alternative plain-text links. In case the user’s client shows plaintext fallback, include actual URLs in the content.  
  - Always include meaningful `alt="..."` text on `<img>` tags. If images are blocked, the alt text gives context (and helps avoid broken layout). This is critical for accessibility and spam filtering【39†L94-L101】.  
  - Fallback background colors. If you use a background image, also set a solid `background-color` inline, so that if the image is disabled you still have a decent background【37†L211-L219】【37†L220-L224】. (Bulletproof background techniques and HTML/CSS gradients can mimic images.)  
  - Bulletproof (code-based) buttons. Instead of an image button, use an `<a>` or `<button>` styled with inline CSS (padding, background-color, border) so it still shows if images are off【37†L248-L257】.  
  - Conditional HTML for Outlook if needed. For advanced styling like VML backgrounds or exclusive Outlook layouts, wrap that code in MSO comments (`<!--[if mso]>…<![endif]-->`) so only Outlook sees it【17†L204-L212】【17†L227-L236】.  
  - Media queries for responsiveness. Many mobile and modern webmail clients (Gmail app, iOS Mail, Outlook mobile) support `@media` queries【3†L345-L353】. Use them to adjust font sizes or single-column layouts on small screens. Always test to see which clients in your audience respect them.  
  - Testing and fallback plan. As Litmus advises, because “every email can display in 300,000+ ways,” always preview and test your email in multiple clients【27†L309-L318】. 

- **Avoid:**  
  - **JavaScript or `<script>` tags.** JavaScript is stripped by all major email clients for security【27†L297-L304】. Any dynamic behavior must be omitted.  
  - **External CSS (`<link>` tags) or `<style>` in body.** Most clients either ignore linked stylesheets or move `<style>` into the head. As noted, Gmail only processes CSS in the head or inline【21†L174-L182】【3†L311-L319】. Keep all CSS inline or in a single `<style>` block in the `<head>`.  
  - **Complex or unsupported CSS properties:** Avoid floats, position, many CSS3 features, and margin on non-text elements. For instance, Outlook ignores floats and margin/padding on `<div>`s【13†L339-L347】. Do not rely on `flex`, `grid`, or CSS animations. (Apple Mail may support some, but many clients do not.)  
  - **Background images.** As noted, clients like Outlook desktop block images by default【37†L211-L219】. Avoid text-over-image designs unless you provide fallback.  
  - **Non-web-safe fonts or excessive web fonts.** Since many clients only render standard fonts, don’t count on fancy custom fonts (and never use `@font-face` without a fallback)【27†L412-L417】. Some mobile apps ignore web fonts altogether.  
  - **Video, Flash, forms, and scripts.** These interactive or multimedia elements are not supported in most inboxes. Video is only safe in a few (like Apple Mail)【32†L182-L190】; in others it will be ignored.  
  - **Hidden/preheader tricks that break clients.** Some email build techniques (like elaborate preheader hacks or invalid CSS) can cause clients to chop off the top of the email. Test carefully to ensure the opening looks intact.  
  - **Long code lines or improper syntax.** Gmail’s parser can break if an inline CSS declaration is malformed (e.g. missing spaces)【21†L242-L250】. Always validate your HTML/CSS to avoid invisible errors.  
  - **Large, unoptimized images.** Big images slow load and may be blocked. Compress images to web resolution (≈72 dpi) and use dimensions in HTML to avoid layout shifts.  
  - **Too-wide layouts.** Stick to ~600px width or less; going wider often causes horizontal scrolling or clipping in clients like Yahoo and Outlook【32†L177-L185】【39†L53-L58】.

By following these guidelines – using simple table layouts, inline styles, fallback fonts/colors and avoiding unsupported tricks – you’ll minimize “disturbed” rendering. In practice, always test in real clients. As Litmus and Email on Acid stress, “even well-designed emails can break” without thorough cross-client testing【27†L309-L318】【37†L248-L257】.
